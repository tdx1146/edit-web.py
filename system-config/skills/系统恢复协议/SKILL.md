## 适用场景

AI 被截断/重启/回滚后，需要恢复系统功能时。不适用于日常对话或例行维护。

## 协议五步

### 第一步之前：动手前三问
在执行五步之前，先问自己三个问题：

1. **当前方案在工作吗？** — 如果在工作，第一反应不应该是「改」，应该是「确认我在理解它」。
2. **想解决问题还是想证明自己？** — 后者就停。解决问题的正确路径通常比证明自己的路径短。
3. **抄旧代码 dandan 会说我做得对吗？** — 会就不改。不会才说明旧代码确实有问题。

这三问不是限制行动，是过滤噪音。过滤完之后再动，动的就是对的。


### 第一步：不动代码（前 10 轮不做任何修改）
- 不修改 `.py` / `.html` / `.mjs` 文件
- 不动 cron 配置
- 不动 Gateway 配置
- 不动模型配置

### 第二步：确认用户需求
- 用户说「XX坏了」时，先问「正常的XX应该是什么样的？」
- 用自己的话复述一遍用户的需求描述，让用户确认
- 确认前不猜测问题原因

### 第三步：找对基线
- 确定问题出现的时间窗口
- 到 `找回自己/` 里找那个窗口之前的备份
- 确认备份的 API 模式（store/api.*/原生fetch）与当前兼容
- 不兼容 → 手动移植关键逻辑，不全量替换
- **正确基线不是最早的备份，是最近功能可用的备份**

### 第四步：单变量验证
- 一次只改一个东西
- 改完让用户测，确认有效再改下一个
- 标准：「有效」= 用户说好了，不是你测着觉得好了

### 第五步：事后记录
- 恢复过程中所有的误判和修正路径写入 `memory/`
- 更新 facts.dict.md 方法论断言
- 打包到找回自己/ 
- 更新系统全图.md 变更记录

## 常见错误模式

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 恢复期顺手优化 | 用户感知到变化，以为是新bug | 先恢复原样，再独立讨论优化 |
| 在当前层反复修 | 三次修不好同一个问题 | 立即升层问「用户实际要什么」|
| 用最早备份恢复 | 丢失后续功能 | 用最近可用备份 |
| 改多个变量同时验证 | 不知道哪个修好了 | 一次改一个 |
